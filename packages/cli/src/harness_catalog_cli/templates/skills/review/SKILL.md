# review — 스킬 심사와 다듬기

스킬 하나를 읽고 "발견되는가, 읽히는가, 따를 수 있는가, 팀 규약에 맞는가"를 점검표(`references/checklist.md`)로 판정해 표로 낸다. 점검표의 문면은 그 파일이 소유하고 항목마다 출처(스펙·Anthropic·Codex·팀)가 붙어 있다 — 본문은 가리킬 뿐 다시 쓰지 않는다. 결정적인 검사(`hc check`, 줄 수, evals 실행)를 먼저 돌리고, 판단이 드는 항목은 본문을 인용해 근거를 적는다. 고치는 일은 사용자가 항목을 고른 뒤 브랜치에서 하고, 병합은 사람이 한다.

## 언제 쓰는가

- 쓴다: "이 스킬 점검해줘", "스킬 리뷰해줘", "왜 이 스킬이 발동 안 해?", "스킬 다듬어줘", "리팩토링해줘", 갱신 PR을 올리기 전 자기 심사.
- 쓰지 않는다: 새 스킬·도구를 만드는 것은 `write`다. "SKILL.md의 '뽑아줘'를 '추출해줘'로 바꿔줘"처럼 자리와 내용이 정해진 수정은 심사 없이 갱신 경로(브랜치 → 수정 → PR)다. 도구(`tool.json`)의 계약은 `hc check` 항목 11과 `write`의 tool-contract가 보므로 여기서 보지 않는다.

## 단계

1. **대상과 판을 정한다.** 카탈로그 클론의 `skills/<name>/`이 우선이다. 클론이 없으면 `get_skill(<name>)`으로 본문과 `files`를, `get_skill(<name>, path=<참조 파일>)`로 참조 파일을 읽는다. 어느 판(sha)을 보는지 적는다.
2. **결정적 검사를 먼저 돌린다.** 클론이면 `hc check`(항목 3 SKILL.md 스펙, 7 크기). 그리고 센다: SKILL.md 본문 줄 수(500 안), description 글자 수(1024 안), 참조 링크의 깊이(SKILL.md에서 한 단계), 100줄 넘는 참조 파일의 목차 유무, 경로의 슬래시. 붉은 것은 표의 맨 위에 둔다. 2~5는 읽고 돌릴 뿐 파일을 바꾸지 않는다 — 바꾸는 것은 7뿐이다.
3. **점검표를 항목별로 판정한다.** `references/checklist.md`의 A~E를 차례로. 표의 열은 넷이다: 항목 | 판정(통과 · 수정 · 해당 없음 · 판단 필요) | 근거(본문에서 인용한 한 줄, 없으면 "없음") | 제안(한 문장). 흔들리는 항목은 "수정"으로 밀지 말고 "판단 필요"에 이유를 적는다. 항목끼리 당기는 경우(간결하게 vs 자유도를 낮추어 자세히)는 그 스킬의 과제가 좁은 다리인지 열린 들판인지로 가른다(점검표 C2).
4. **발동 문제면 description에 집중한다.** 사용자가 실제로 한 말(세션 로그가 있으면 그 문장)과 description의 낱말을 나란히 놓고, 말에는 있는데 description에 없는 낱말을 찾는다. 발동 낱말은 description의 앞쪽에 있어야 한다 — 호스트가 긴 description을 잘라 낼 수 있다(점검표 A3).
5. **evals를 본다.** 쌍이 있으면 `harbor run -p skills/<name>/evals -a oracle -e docker`로 전 케이스 reward 1인지. 모델 자격이 있는 곳이면 `harbor run --path skills/<name>/evals --agent <하네스> --env docker --skill ./skills/<name>`(있이)과 `--skill` 없이(없이) 두 번. 없이도 전부 통과하면 "스킬이 하는 일이 없다"로 적는다 — 2회 연속이면 폐기 후보(E3). 쌍이 없으면 "evals 없음"으로 적고 `write` 4단계의 scaffold로 쌍을 만들기를 제안한다.
6. **보고하고 멈춘다.** 표와 한 줄 결론("이대로 둔다 / 고칠 항목 n개 / 폐기 후보"). 사용자가 고칠 항목을 고른다.
7. **고치기로 하면** 브랜치 `review/<name>`을 따고 description부터 고친다(발견이 먼저다). 그다음 본문. 고친 뒤 `hc check`와 5를 다시 돌려 표의 판정을 갱신한다. 사람 승인 전까지는 되돌릴 수 있는 일만 한다 — 그 줄에 오면 루프는 멈춘다(needs_human). "올려"라고 할 때만 커밋·push·`gh pr create`. 병합은 사람이 git 호스트에서 한다.

## 실패 대응

| 상황 | 대응 |
|---|---|
| `search_skills(<name>)`에 없다 | 은퇴했거나 이름이 다르다. 비슷한 이름을 보이고 멈춘다 |
| 레지스트리에 연결이 안 된다 | 클론 경로를 묻는다. 둘 다 없으면 멈춘다 |
| `hc check`가 붉다 | 표의 맨 위에 항목 번호와 사유를 적고 6에서 멈춘다. 고치는 것은 사용자가 고른 뒤 7에서 — 붉은 항목부터 |
| evals가 없다 | 표에 "evals 없음"을 적고 `write`의 scaffold로 쌍을 만들기를 제안한다. 심사는 계속한다 |
| Harbor가 없거나 모델 자격이 없다 | Oracle까지만 돌리고 표에 "있이·없이 미실행"을 적는다 |
| description이 1024자를 넘거나 본문이 500줄을 넘는다 | 수정 항목 맨 위에 둔다. 본문은 참조 파일로 나누되 한 단계 깊이를 지킨다 |
| 스킬에 `scripts/`가 있다 | 이유 한 줄이 있으면 통과(루프는 집지 않는다). 없으면 "결정적 부분이면 `tools/`로, 세션 전용이면 이유 한 줄"을 제안한다(D2) |
| 점검표 항목이 서로 당긴다 | "판단 필요"에 두 항목과 이유를 적는다. 하나를 고르는 것은 사용자다 |
| 클라우드 샌드박스 세션 | 6에서 멈춘다. 고치기는 로컬 세션에서 |
