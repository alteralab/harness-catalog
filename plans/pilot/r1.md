# r1 — Dex v2.45.1의 그랜트 셋과 토큰 클레임 실물 (pilot Q2 (a)(b), Q5, Q2 (c) 일부)

## 질문

- Q2(a) 장치 흐름이 `public: true` 클라이언트로 되는가.
- Q2(b) 클라이언트 자격 증명 토큰의 `sub`·`azp`·`groups` 실물.
- Q2(c) 그룹이 `groups` 클레임에 실리는가 — **정적 사용자(staticPasswords)로만**. LDAP 연합 판은 NAS가 닿을 때 r2.
- Q5 서비스 주체 판별의 표지와 무인 클라이언트 등록 절차.
- 덤으로 잰 것: `resource` 파라미터와 `aud`, 설계 스코프 `skills:read`, PKCE 서버 강제, 액세스 토큰 형식, 리프레시 토큰의 수.

## 방법

```sh
cp .env.example .env   # 비밀 넷은 openssl rand -base64 24
docker compose -f docker-compose.dev.yml up -d        # postgres:17-alpine + ghcr.io/dexidp/dex:v2.45.1, docker/dex/config.yaml(정적 사용자 둘·클라이언트 다섯)
set -a; . ./.env; set +a
uv run --script tools/pilot/dex_grants.py --issuer http://localhost:5556/dex \
  --ci-secret "$DEX_CI_RUNNER_SECRET" --resource "$HC_PUBLIC_URL"      # 관측마다 JSON 한 줄
```

도구는 Dex에 실제 HTTP를 보내고 로그인 폼을 POST로 채운다(레지스트리 흉내 없음). 리프레시 토큰 수 실험은 같은 모듈을 import한 10줄 스크립트로 세 번 로그인해 잰 것이며 관측 절에 결과만 적었다.
Dex 소스 확인은 `git clone --depth 1 --branch v2.45.1 https://github.com/dexidp/dex`의 `server/server.go`·`server/oauth2.go`·`server/deviceflowhandlers.go`·`cmd/dex/config.go`·`cmd/docker-entrypoint/main.go`.

리프레시 토큰 수 실험(같은 사용자 `dev@example.com`, 공개 클라이언트, `client_id`만 보낸 `refresh_token` 그랜트):
- 로그인 A → A 리프레시: `200`.
- 로그인 A, 다시 로그인 B(같은 클라이언트 `claude-code`) → A 리프레시: `400 invalid_request "Refresh token is invalid or has already been claimed by another client."`, B 리프레시: `200`.
- 로그인 A(`claude-code`), 로그인 C(`codex`) → A 리프레시: `200`.
- 리프레시 요청에 `client_secret=`(빈 값)을 붙이거나 `Authorization: Basic claude-code:`를 쓰면 같은 400. 공개 클라이언트는 폼의 `client_id` 하나만 보내야 한다.

소스 확인(문면이 아니라 실물 코드):
- `server/server.go` `allSupportedGrants` = authorization_code·refresh_token·device_code·token-exchange(+ implicit은 response_type, password는 `passwordConnector`). **client_credentials 없음.** `cmd/dex/config.go`의 `oauth2.grantTypes`에 적어도 걸러진다.
- `server/oauth2.go` `getAudience`: `aud` = client_id, 또는 스코프 `audience:server:client_id:<peer>`를 요청하면 `[peer, client_id]` + `azp`. `resource` 파라미터를 읽는 코드 없음.
- `server/deviceflowhandlers.go:342` `client.Secret != deviceReq.ClientSecret` — 공개 클라이언트는 둘 다 빈 문자열이라 통과. `/device/token` 폴링은 클라이언트 인증 없이 `device_code`(+`code_verifier`)만.
- `server/oauth2.go` `newAccessToken` = `newIDToken(...)` — 액세스 토큰은 ID 토큰과 같은 서명 JWT(클레임 같음, `nonce` 없음).
- `cmd/dex/config.go`에 PKCE 강제 설정 없음. `code_challenge`가 오면 검증하고, 안 오면 그냥 발급(`a2.no_pkce_public`).
- `cmd/dex/config.go` `expandEnvInMap`은 `storage.config`·`connectors[].config`·`signer.config`에만 돈다. `issuer`·`staticClients`의 `$VAR`는 글자 그대로 남는다(첫 기동에서 `"issuer":"$DEX_ISSUER"`로 404 확인). 이미지 entrypoint(`cmd/docker-entrypoint/main.go`)는 `dex serve <file>.yaml`의 파일을 gomplate로 먼저 렌더링하므로 `{{ getenv "VAR" }}`가 맞는 문법이다. 클라이언트는 `idEnv`·`secretEnv`도 된다.

## 판정

| 질문 | 판정 | 기준 대조 |
|---|---|---|
| Q2(a) 장치 흐름, 공개 클라이언트 | **답: 지원** | `d.device_code_public` 200 → 승인 → `d.device_token_public` 200, `client_secret` 없이. 이슈 #3983의 증상은 v2.45.1에서 재현되지 않았다. 브라우저 없는 샌드박스 경로는 v3.0 범위에 남는다 |
| Q2(b) 클라이언트 자격 증명 토큰 | **답: Dex가 그랜트를 지원하지 않는다** (`b.client_credentials` 400 `unsupported_grant_type`, discovery `grant_types_supported`에 없음, 소스 확인) | DESIGN §2 "클라이언트 자격 증명은 플래그로 켠다"는 문면 오류. 무인 읽기 주체의 토큰 취득 방식은 사용자 결정(우산 §6-10) |
| Q2(c) 그룹 클레임 (정적 사용자) | **부분 답**: 가입자 `groups: ["skills-readers"]`, 비가입자는 **클레임 부재**(빈 배열 아님) | DESIGN §2 "그룹 클레임이 빠진 사람 토큰은 not_a_member" 규칙에 맞는다. LDAP 평탄화는 r2 |
| Q5 서비스 주체 표지 | **재정의 필요**: 클라이언트 자격 증명 토큰이 없으므로 "`sub`∈client ID 집합" 표지는 성립할 수 없다. §6-10 결정이 정하는 방식에 따라 표지가 정해진다(권고안: 전용 LDAP 계정 + 장치 흐름 1회 + 리프레시 → 표지는 `sub`가 그 계정 또는 `azp`/`aud`=`ci-runner`) | 등록 절차(정적 클라이언트 한 항목)는 `docker/dex/config.yaml`에 있고 재현됐다 |
| `aud`와 `resource` | **관측**: `resource` 무시, `aud`=client_id. 교차 클라이언트 스코프를 요청하면 `aud`에 레지스트리 URL이 실리지만 MCP 클라이언트가 그 스코프를 보낼 근거가 없다 | DESIGN §2 "`aud`가 레지스트리 canonical URI"는 Dex로는 하네스 쪽 협조 없이 불가. 사용자 결정(우산 §6-11) |
| 스코프 `skills:read` | **관측**: `invalid_scope`. Dex는 `openid email groups profile offline_access` + 교차 클라이언트 스코프만 낸다 | DESIGN §2의 스코프 하나(`skills:read`)는 Dex가 발급할 수 없다. 사용자 결정(우산 §6-12) |
| PKCE 서버 강제 | **관측**: 불가(설정 없음). 클라이언트가 보내면 검증 | distribution D6 수정 |
| 액세스 토큰 | **관측**: 서명 JWT, ID 토큰과 같은 클레임, `expires_in` 3599 | 레지스트리의 PyJWT 검증(service D7)이 성립한다. D7 토큰 수명 1시간 확인(V4 일부) |
| 리프레시 토큰 | **관측**: 사용자·클라이언트 쌍당 하나. 같은 사람이 같은 하네스로 두 번째 머신에서 로그인하면 첫 머신의 리프레시가 죽는다 | 사용자 안내 문장(Q12·docs)에 적는다. 액세스 토큰 1시간은 살아 있다 |

## 설계 영향

DESIGN §11 행 셋이 필요하고 전부 사용자 결정이다(우산 §6-10·11·12에 올렸다). 그 전까지 service P1의 OIDC 어댑터는 `iss`·서명·`exp`만 확정이고 `aud`·스코프·주체 표지는 미정이다. distribution D5·D6·D8은 PLAN 판정이라 바로 고쳤다.
